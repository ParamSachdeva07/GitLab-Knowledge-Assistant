[SBOM backfiller](https://gitlab.com/gitlab-org/sbom/systems/backfiller) is a stop-gap solution to assist with [Missing SBOMs for GitLab Security release](https://gitlab.com/components/sbom/generator/-/issues/24).

It runs automatically from the `backfill` CI job on a pipeline schedule. On each run it compares each source project's release tags against the SBOM packages that exist, creates the ones that are missing, and is idempotent, so an interrupted run is safe to repeat. The one thing it cannot create is an SBOM for a release whose omnibus version manifest has not been published, because the SBOM generator needs that manifest. When that happens it opens a tracking issue, and the failed run posts an alert to the team's Slack channel.

This runbook covers the manual part: fixing a missing omnibus manifest so the backfiller can generate the SBOM. The repository is the canonical reference for everything else:

- [`README`](https://gitlab.com/gitlab-org/sbom/systems/backfiller/-/blob/main/README.md) documents the tool's behaviour, tracking issues, `ignore_tags`, and the Slack channels used for alerts and escalation.
- [`sbom-backfill-triage`](https://gitlab.com/gitlab-org/sbom/systems/backfiller/-/blob/main/skills/sbom-backfill-triage/SKILL.md) explains what each line of a run's output means and what to do about it.
- [`sbom-missing-manifest`](https://gitlab.com/gitlab-org/sbom/systems/backfiller/-/blob/main/skills/sbom-missing-manifest/SKILL.md) covers confirming and escalating a missing manifest, or deciding the tag belongs in `ignore_tags`.

## Fix Missing Omnibus Manifests

**Context:** Manifests are generated by the `manifest-upload` CI job on `dev.gitlab.org` during release pipelines. When that job fails, the manifest is never published to the [manifests page](https://gitlab-org.gitlab.io/omnibus-gitlab/gitlab-manifests/manifests.html), which blocks SBOM generation. We can retry that job by hand, but the retry cannot be automated, so it stays a manual step.

---

### Step 1 — Identify the Missing Manifests

The backfiller identifies these for you: a missing manifest is reported in the run log as `⏩ Skipping creation of SBOM ... because manifest is unavailable`, and each blocked version is named in an open tracking issue labelled `sbom-backfill-tracking`. The [`sbom-backfill-triage`](https://gitlab.com/gitlab-org/sbom/systems/backfiller/-/blob/main/skills/sbom-backfill-triage/SKILL.md) skill explains the run output. You can also cross-check the [manifests page](https://gitlab-org.gitlab.io/omnibus-gitlab/gitlab-manifests/manifests.html) against expected release versions to see which are missing.

### Step 2 — Confirm the Manifest Is Really Missing

The manifest may have been published since the run that reported it, so confirm it is still missing before doing any work:

```bash
curl -sf "https://gitlab-org.gitlab.io/omnibus-gitlab/gitlab-manifests/gitlab-ee/<MAJOR.MINOR>/<VERSION>-ee.0-ee.version-manifest.json" \
  && echo "OK" || echo "MISSING"
```

If it returns the manifest, there is nothing more to do: the next scheduled run creates the SBOM and closes the tracking issue on its own.

### Step 3 — Find the Failed `manifest-upload` Job on dev.gitlab.org

For each still-missing version, locate the corresponding release pipeline on `dev.gitlab.org/gitlab/omnibus-gitlab` and look for a failed or skipped `manifest-upload` job. Its log may show a transient error such as:

```text
fatal: remote error: GitLab is currently unable to handle this request due to load
```

### Step 4 — Retry the Failed `manifest-upload` Job(s)

On `dev.gitlab.org`, manually retry each failed `manifest-upload` job for the affected versions. As of [omnibus-gitlab!9525](https://gitlab.com/gitlab-org/omnibus-gitlab/-/merge_requests/9525), the job has `retry: 2` configured, so transient failures should self-heal; a manual retry covers the cases it does not.

1. Navigate to the job URL on `dev.gitlab.org`
1. Click **Retry**
1. Confirm the job succeeds

This retry is not automated, so it stays a manual step. If the manifest is missing for a reason a retry will not fix (the release was superseded or re-tagged, or a wider publishing problem affecting a whole minor version), escalate instead by raising an issue with an SRE or asking the release team in Slack. The [`sbom-missing-manifest`](https://gitlab.com/gitlab-org/sbom/systems/backfiller/-/blob/main/skills/sbom-missing-manifest/SKILL.md) skill covers confirming which case you are in and where to escalate.

### Step 5 — Trigger the `Generate licence pages` Scheduled Pipeline

A successful `manifest-upload` publishes the manifest, but it is not readable until the manifests index is regenerated, which is a separate step. Trigger the [`Generate licence pages` scheduled pipeline](https://gitlab.com/gitlab-org/omnibus-gitlab/-/pipelines) on `gitlab.com`. Specifically, the `pages` job within it regenerates the manifests index and publishes the JSON files.

1. Go to **CI/CD > Schedules** in `gitlab-org/omnibus-gitlab`
1. Run the `Generate licence pages` schedule manually, or wait for its next scheduled run
1. Monitor the `pages` job to confirm it completes successfully

We do not automate this step. It only helps once the `manifest-upload` retry in Step 4 has succeeded, and that retry is manual, so automating this step alone would still leave the manual retry in front of it, with nothing to gain.

### Step 6 — Verify the Manifests Are Published

This check is optional. Re-checking the manifest is the backfiller's own first step on every run, so the next scheduled run repeats this exact check for each blocked version and acts on the result, creating the SBOM once the manifest is present. That run is the authoritative verification. To confirm immediately without waiting for it, for each previously missing version:

```bash
curl -sf "https://gitlab-org.gitlab.io/omnibus-gitlab/gitlab-manifests/gitlab-ee/<MAJOR.MINOR>/<VERSION>-ee.0-ee.version-manifest.json" \
  && echo "OK" || echo "MISSING"
```

You can also check the [manifests index page](https://gitlab-org.gitlab.io/omnibus-gitlab/gitlab-manifests/manifests.html) lists all expected versions.

### Step 7 — Close Out

Once the manifest is published, the next scheduled run creates the missing SBOM and closes the tracking issue automatically, with no further action. Do not close the tracking issue by hand; the backfiller closes it once every version in its title has an SBOM package.

If a version can never get a manifest (the release was superseded, re-tagged, or has corrupt artifacts), it belongs in `ignore_tags` in `bin/backfill` instead, so it is not reported every run. This is a judgement call about a security release deliberately having no SBOM, so it's best to get a second opinion first. The criteria are in 'Adding an entry to `ignore_tags`' in the [README](https://gitlab.com/gitlab-org/sbom/systems/backfiller/-/blob/main/README.md).

### What's Automated and What Isn't

| Task | Status | Notes |
|---|---|---|
| Detect missing SBOMs and manifests | Automated | Scheduled `backfill` job compares release tags against SBOM packages |
| Create SBOMs once the manifest exists | Automated | Idempotent, so a re-run is safe |
| Track and alert | Automated | Opens and closes tracking issues; a failed run posts a Slack alert to the team |
| Retry the `manifest-upload` job on `dev.gitlab.org` | Manual only | Not automated; retry by hand |
| Trigger `Generate licence pages` | Scheduled or manual | Runs on its own daily schedule, or can be triggered by hand; downstream of the Step 4 retry |
| Escalate a manifest a retry will not fix | Manual | Raise an issue with an SRE or ask the release team in Slack |
